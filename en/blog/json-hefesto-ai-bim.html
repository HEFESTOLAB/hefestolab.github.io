JSON HEFESTO: towards AI-native BIM

BIM models contain enormous amounts of information. The problem is that information is not always represented in a form a language model can read, connect and modify directly. JSON HEFESTO is being designed to reduce that gap.

7 August 2026HEFESTOLABTechnical read · 10 min
Core ideaThe goal is not to replace IFC or turn an LLM into an uncontrolled geometric modeller. The goal is to give the project a compact, explicit operational representation that AI can reason over and propose changes to, while HEFESTO performs deterministic validation.

The problem is not missing information — it is access to it

A BIM authoring file may contain geometry, types, materials, levels, systems, parameters, quantities and relationships. For a traditional BIM application that is normal: the software understands its own internal format and exposes an API for querying it.

For an LLM the situation is different. A native authoring file is not, simply because it contains BIM, a language that Claude, ChatGPT or Gemini can interpret directly. In most workflows the file must be opened by the corresponding application, accessed through an API, exported, or translated into a data layer the model can process.

That creates friction for the next generation of AEC software. If every AI interaction starts with “open the application, extract X, transform Y, re-import Z”, intelligence remains outside the model. HEFESTO starts from a different premise: the working representation of the project should also be understandable by automated processes and agents.

IFC solved a different problem — and remains fundamental

IFC is an open, vendor-neutral international standard. Its primary role is to let different applications exchange a digital description of the built environment. That role is essential and HEFESTO is not trying to replace it.

But a universal exchange standard has different requirements from an operational representation designed for an AI agent. The most common IFC serialization uses STEP Physical File: machine-readable text with entities, ordered attributes and many references between objects. It is extremely powerful for interoperability, but can be verbose and expensive to traverse as direct LLM context.

buildingSMART also supports other serializations and technologies around IFC, including JSON. Changing syntax alone, however, does not remove the breadth of the standard, the reference graph or the need to interpret a schema designed to cover a very large domain.

So the right comparison is not “JSON HEFESTO versus IFC”.IFC is an open exchange layer between tools. JSON HEFESTO is HEFESTO's operational representation, designed for working with the project and connecting that project to automation and language models.

What changes when the operational model is JSON designed for AI

JSON by itself solves nothing. A JSON file can be as chaotic as any other data source. The difference lies in designing a structure where relevant project entities, properties and relationships are explicit, coherent and sufficiently compact.

Without publishing the internal schema — which is still evolving — JSON HEFESTO follows a few clear design principles:

Stable identity. Objects should be addressable, comparable across versions and targetable by a specific change.

Explicit semantics. AI should be able to distinguish walls, beams, pipes or equipment and understand which properties make sense for each category.

Understandable relationships. Levels, membership, connections and dependencies should not be hidden inside opaque geometry.

Controlled units and dimensions. Natural language must not introduce numerical ambiguity.

Compact representation. Only information that adds value to the current workflow should travel with the operation.

From a prompt to a validated modification

The potential appears when that representation is combined with an agent. The target workflow is not for an LLM to “edit the file” blindly. It is closer to this:

01Drawing, datasheet or instruction
02LLM interprets intent
03Proposes JSON operations
04HEFESTO validates and executes
05Model and data updated

An instruction such as “change this line diameter”, “raise these columns”, “create a component from this datasheet” or “show me elements without assigned cost” can become a structured operation. AI provides interpretation and reasoning; HEFESTO keeps control of what constitutes a valid change.

This separation is essential: AI proposes; the software validates and executes. Rules for units, categories, references, ranges, connectivity and consistency should not depend solely on the probability distribution of a generative model.

Why file size matters more than it seems

In AI workflows, size is not only a storage concern. It affects transfer, context cost, analysis speed, versioning and the ability to send only the relevant part of a project to a model.

A lightweight representation can be much more useful to an agent than a complete authoring container. In HEFESTO's internal tests, project JSON remains highly compact compared with equivalent BIM authoring or exchange files. We want to normalize models and methodology before publishing comparative numbers, but the trend is clear enough that compactness has become a design criterion.

Compact does not mean poor. It means avoiding redundancy and separating operational information from layers that can be reconstructed, queried or exported when needed.

Beyond “asking questions” to BIM

The real change is not adding a chatbot beside the modeller. It is allowing the language model to work on a project representation that the software itself understands.

That opens an architecture where the same core can help generate an initial project from documentation, review inconsistencies, prepare quantities, create components, compare versions, execute transformations or derive outputs into other ecosystems.

It also reduces dependency on a single AI provider. If the project is expressed as well-structured data, the agent can change: Claude today, ChatGPT tomorrow, Gemini, a local model, or a combination. The asset remains the project and its structure, not the model vendor.

What JSON HEFESTO is not trying to be

It is not a universal replacement for IFC. It is not an international standard. It is not permission to let AI modify a project without checks. And we do not want to publish prematurely a schema that is still evolving with the product.

Its role is more specific: to be HEFESTO's information core and make that core exceptionally easy to use from code, automation and AI agents.

The evolution we are aiming for

For years BIM has focused on enabling professionals to work with information-rich objects. The next stage adds another participant: agents able to interpret documents, reason over thousands of objects and execute tasks under controlled rules.

Doing that well requires more than adding an “AI” button to an existing application. It requires revisiting how the project is represented internally.

JSON HEFESTO is our answer to that question: what would a BIM model look like if, from its birth, it were also designed to be safely read and manipulated by artificial intelligence?
