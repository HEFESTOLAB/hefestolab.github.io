JSON HEFESTO: hacia un BIM nativo para inteligencia artificial

Los modelos BIM contienen una enorme cantidad de información. El problema es que esa información no siempre está en una forma que un modelo de lenguaje pueda leer, relacionar y modificar de manera directa. JSON HEFESTO nace precisamente para reducir esa distancia.

7 agosto 2026HEFESTOLABLectura técnica · 10 min
Idea centralEl objetivo no es sustituir IFC ni convertir un LLM en un modelador geométrico sin control. El objetivo es que el proyecto tenga una representación operativa, compacta y explícita sobre la que una IA pueda razonar, proponer cambios y trabajar junto a HEFESTO con validación determinista.

El problema no es la falta de información: es la forma de acceder a ella

Un archivo BIM de autoría puede contener geometría, tipos, materiales, niveles, sistemas, parámetros, cantidades y relaciones. Para una aplicación BIM tradicional eso es normal: el propio software conoce su formato interno y dispone de una API capaz de consultarlo.

Para un LLM la situación es diferente. Un archivo nativo de autoría no es, por el mero hecho de contener BIM, un lenguaje que Claude, ChatGPT o Gemini puedan interpretar directamente. Normalmente hace falta abrirlo con la aplicación correspondiente, utilizar su API, exportar información o construir una capa intermedia que traduzca el proyecto a datos que el modelo pueda procesar.

Eso crea una fricción importante para la siguiente generación de software AEC. Si cada interacción con IA empieza por “abre la aplicación, extrae X, transforma Y, vuelve a importar Z”, la inteligencia artificial sigue estando fuera del modelo. HEFESTO parte de otra idea: la representación de trabajo del proyecto debe ser comprensible también para procesos automáticos y agentes.

IFC resolvió otro problema — y sigue siendo fundamental

IFC es un estándar internacional abierto y neutral respecto al fabricante. Su función principal es permitir que distintas aplicaciones compartan una descripción digital del entorno construido. Esa función es esencial y HEFESTO no pretende reemplazarla.

Pero un formato de intercambio universal tiene necesidades diferentes a las de una representación operativa pensada para un agente de IA. La serialización IFC más habitual utiliza STEP Physical File: texto legible por máquina, con entidades, atributos ordenados y muchas referencias entre objetos. Es extraordinariamente potente para interoperabilidad, pero puede resultar verboso y costoso de recorrer como contexto directo de un LLM.

buildingSMART también contempla otras serializaciones y tecnologías alrededor de IFC, incluido JSON. Aun así, cambiar la sintaxis no elimina automáticamente la amplitud semántica del estándar, las cadenas de referencias ni la necesidad de interpretar correctamente un esquema diseñado para representar un dominio muy amplio.

Por eso la comparación correcta no es “JSON HEFESTO contra IFC”.IFC es una capa de intercambio abierta entre herramientas. JSON HEFESTO es, dentro de HEFESTO, una representación operativa orientada a trabajar con el proyecto y a conectar ese proyecto con automatizaciones y modelos de lenguaje.

Qué cambia cuando el modelo operativo es un JSON pensado para IA

JSON por sí solo no resuelve nada. Un JSON puede ser igual de caótico que cualquier otro archivo. La diferencia está en diseñar una estructura donde las entidades relevantes del proyecto, sus propiedades y sus relaciones se representen de forma explícita, coherente y suficientemente compacta.

Sin publicar aquí el esquema interno —que además continúa evolucionando—, la filosofía de JSON HEFESTO se apoya en unos principios claros:

Identidad estable. Los objetos deben poder localizarse, compararse entre versiones y ser objetivo de una modificación concreta.

Semántica explícita. Una IA debe poder distinguir que algo es un muro, una viga, una tubería o un equipo y conocer qué propiedades tienen sentido para cada categoría.

Relaciones comprensibles. Niveles, pertenencias, conexiones y dependencias no deberían quedar ocultas dentro de una geometría opaca.

Unidades y dimensiones controladas. La naturalidad del lenguaje no puede implicar ambigüedad numérica.

Representación compacta. Solo debe viajar lo que aporta valor al flujo concreto, evitando arrastrar capas de información que la operación no necesita.

De un prompt a una modificación validada

El potencial aparece cuando esa representación se combina con un agente. El flujo objetivo no es que el LLM “toque el archivo” de forma ciega. Es más parecido a esto:

01Plano, ficha o instrucción
02LLM interpreta intención
03Propone cambios JSON
04HEFESTO valida y ejecuta
05Modelo y datos actualizados

Una instrucción del tipo “cambia el diámetro de esta línea”, “eleva estos pilares”, “crea un componente a partir de esta ficha” o “dime qué elementos no tienen coste asignado” puede convertirse en una operación estructurada. La IA aporta interpretación y razonamiento; HEFESTO conserva el control sobre qué cambios son válidos.

Esta separación es clave: la IA propone; el software valida y ejecuta. Las reglas de unidades, categorías, referencias, rangos, conectividad y consistencia no deben depender únicamente de la probabilidad de un modelo generativo.

Por qué el peso del archivo importa más de lo que parece

En los flujos con IA, el tamaño no es solo un problema de almacenamiento. También afecta a transferencia, coste de contexto, velocidad de análisis, versionado y capacidad de enviar al modelo únicamente la parte relevante del proyecto.

Una representación ligera puede ser mucho más útil para un agente que un contenedor de autoría completo. En las pruebas internas de HEFESTO, el JSON del proyecto se mantiene muy compacto frente a formatos BIM de autoría o intercambios equivalentes. Antes de publicar cifras comparativas queremos normalizar modelos y metodología, pero la tendencia es suficientemente clara como para convertir la ligereza en un criterio de diseño.

Compacto no significa pobre. Significa evitar redundancia y separar la información que necesita el flujo operativo de otras capas que pueden reconstruirse, consultarse o exportarse cuando sean necesarias.

Más allá de “preguntarle cosas” al BIM

El verdadero cambio no consiste en abrir un chatbot al lado del modelador. Consiste en permitir que el modelo de lenguaje trabaje sobre una representación del proyecto que también entiende el software.

Eso abre una arquitectura donde un mismo núcleo puede servir para generar un proyecto inicial a partir de documentación, revisar incoherencias, preparar mediciones, crear componentes, comparar versiones, ejecutar transformaciones o derivar salidas hacia otros ecosistemas.

Y, sobre todo, reduce la dependencia de un único proveedor de IA. Si el proyecto está expresado en datos bien estructurados, el agente puede cambiar: Claude hoy, ChatGPT mañana, Gemini, un modelo local o una combinación de ellos. El activo sigue siendo el proyecto y su estructura, no el proveedor del modelo.

Lo que JSON HEFESTO no pretende ser

No es un sustituto universal de IFC. No es un estándar internacional. No es una licencia para dejar que una IA modifique un proyecto sin comprobaciones. Y tampoco queremos publicar prematuramente un esquema que todavía está evolucionando junto con el producto.

Su función es más concreta: ser el núcleo de información de HEFESTO y hacer que ese núcleo sea excepcionalmente fácil de utilizar por código, automatizaciones y agentes de IA.

La evolución que buscamos

Durante años el BIM se ha centrado en que diferentes profesionales trabajen sobre objetos ricos en información. La siguiente etapa añade otro participante: agentes capaces de interpretar documentos, razonar sobre miles de objetos y ejecutar tareas bajo reglas controladas.

Para que eso funcione bien no basta con añadir un botón “AI” a una aplicación existente. Hace falta revisar cómo representamos el proyecto desde dentro.

JSON HEFESTO es nuestra respuesta a esa pregunta: ¿cómo sería un modelo BIM si desde su nacimiento también estuviera pensado para ser leído y manipulado de forma segura por inteligencia artificial?

Seguiremos publicando el proceso.En próximos artículos mostraremos casos de interoperabilidad, experimentos Revit ↔ JSON, Component Studio y la arquitectura MCP de HEFESTO, separando siempre lo que ya funciona de lo que todavía está en desarrollo.
